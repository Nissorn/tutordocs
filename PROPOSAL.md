## The goal

One lean macOS app for studying, exam prep and interview prep, replacing NotebookLM plus scattered tools. Notion-feeling UI without the clutter, without hand-built databases and manual tags, and without the features you never use. Content and visuals generated by the coding agents already on this machine, not by paid API keys or dedicated image/video models. Chapters as a textbook or a course, in interactive or plain markdown mode, with quizzes and remembered progress. Rust first so other OSes come later.

## The decision

**Port the engine to Rust. Two languages, no Python runtime.** This is your round-2 choice, made against my recommendation to reuse DeepTutor's running backend. I record the cost honestly rather than relitigate it.

What you gain is a single lean native binary, Rust owning the learning logic as you wanted, and no Python process to supervise, package, sign and version. What you pay is rebuilding ingestion, the mastery and spaced-repetition model, grading orchestration, the agent drivers and the visualizer host. Those are solved problems in DeepTutor, so the work is translation rather than invention.

**Port, do not reinvent.** DeepTutor is Apache-2.0 (`LICENSE:190`, © 2025 Data Intelligence Lab, HKU), which permits translating its Python into Rust with attribution. Its provider code carries hard-won detail worth carrying across rather than rediscovering. Two examples I read directly: `_INLINE_SYSTEM_PROMPT_LIMIT = 8_000` exists because Windows caps a command line at 32,767 characters and a longer spawn fails with WinError 206, which the SDK misreports as "Claude Code not found"; and `_ClaudeCodeSession` runs a dedicated owner task because `ClaudeSDKClient` enters anyio task groups in `connect()` and must leave them from the same task. Rust will not have the anyio constraint, but it will have the command-line limit and its own session-ownership questions. Read that file before writing the driver.

Notion's own architecture supports the webview shape regardless of the engine decision. Ghidra Deep-mode analysis of `/Applications/Notion.app` found a thin Electron 44.9.1 shell whose main window loads `app.notion.com`, evidenced by the `client_placeholder` renderer and the `https_app.notion.com_0` IndexedDB origin. The Notion UI you like is web technology already. A Tauri webview is the same idea with a leaner shell and no remote origin.

## Architecture

Rust owns the window and webview lifecycle, the custom-protocol asset server, capability enforcement for untrusted artifacts, the markdown folder as content truth, SQLite for progress and annotations, ingestion, the agent drivers, the mastery and spaced-repetition engine, grading orchestration, and the visualizer host. TypeScript owns the reader surface and every visual. There is no third runtime.

The shell worker's estimate for a Tauri reader is 70-85% TypeScript and 15-30% Rust by line count (labelled estimate, not measured). Porting the engine to Rust shifts that ratio toward Rust, because the learning logic is now Rust code rather than a reused service. The visual JavaScript stays TypeScript no matter what, because WebKit executes it.

### No index, by decision

You chose to have the coding agent search the folder itself, with no vector DB, no embeddings and no FTS. This is the load-bearing simplification and it directly answers your complaint about having to build and maintain databases by hand.

The markdown folder is the store. The agent is the query engine. It already knows how to grep, glob and read files, and it does that better than a keyword index for a personal library of a few hundred chapters. There is no index to keep in sync, no embedding model to download, no Ollama process to keep running, and no schema for you to customize. Retrieval quality becomes a prompt-and-folder-layout problem rather than an infrastructure problem.

The cost is that every retrieval burns agent quota and takes agent latency, and there is no instant type-ahead search over the library. If that becomes painful, SQLite FTS5 is a cheap addition later, because the folder layout does not change. Do not build it now.

### Lazy, outline-first generation

You chose outline first, then a chapter generated when you open it. The agent writes `course.json` with the outline, objectives and chapter order, and each chapter directory starts as a placeholder. Opening a placeholder triggers one agent job that writes the markdown and its visuals. This keeps the initial quota burn small, shows you the whole course before you invest in it, and lets you redirect the outline cheaply. Notion's own `client_placeholder` and `darkmode_placeholder` renderer windows are the precedent for painting a cheap skeleton while real content loads.

### The reading surface

Three columns, per your round-2 choice. A sidebar tree of courses and chapters, a centered document, and margin notes on the right. Typography carries the Notion resemblance now that the editor is gone, so the reading column width, line height, heading scale and spacing are the details that matter. Chrome stays minimal. Open a chapter, highlight, write a margin note, answer a quiz. Nothing else earns a permanent control.

Interview prep is the same surface. The agent writes the content, you answer free-text, the agent grades and explains. No separate mock-interview interaction, no flashcard mode. DeepTutor's `practice.py`, `question.py` and `quiz_judge.py` are the design reference for the grading loop, translated to Rust orchestration over an agent driver.

**One rule worth stealing from memorilla.** Its PV4 benchmark writes every question so that answering requires combining at least two facts the sources show but never state (`README.md:190-191`, verified directly). That is a prompt constraint, not infrastructure, and it is the difference between a quiz that tests recall and one that tests understanding. Adopt it for both quiz and interview generation: every question must require synthesizing at least two facts from the chapter, and the grader checks the synthesis rather than keyword overlap. It costs nothing and needs no embeddings.

## The data shape

Four aggregates and one truth rule.

**Library.** A folder you choose, holding `sources/` for imported PDF, markdown and URL captures, `chapters/<id>/` for agent-written markdown plus a `visuals/` directory, and `course.json` for the outline, chapter order and objectives. The markdown files are the source of truth. Anything derived is a rebuildable cache, and under the no-index decision there is almost nothing derived.

**Annotation.** An anchor plus a payload. The anchor is a W3C text quote selector with a position fallback, copied field for field from DeepTutor's `reading/models.py` rather than invented. The payload is a highlight color, a margin note or a bookmark. On regeneration the host re-anchors by quote match and flags every mark that fails, surfacing the `ReadingUpgradeConflict` case for you to resolve. Nothing is deleted silently.

**Mastery.** An append-only event log per objective plus a derived repetition state. The verified DDL is `mastery_events(id, path_id, revision, event_type, payload_json, session_id, turn_id, created_at)` at `learning/storage.py:571-580`, eight columns indexed on `(path_id, revision, id)`. This proposal previously listed seven columns and cited `storage.py:161`; both were wrong and I re-read the DDL to correct them.

Port `learning/mastery.py`, not `QuizAttempt.mastery_estimate`. That field is vestigial at this commit. A repo-wide grep finds only its declaration at `learning/models.py:134` defaulting to 0.0 and one test asserting it stays 0.0, so nothing in production ever populates it. The live model is `compute_mastery` at `learning/mastery.py:24` over `_RECENCY_WEIGHTS = (0.5, 0.7, 0.85, 0.95, 1.0)` at `:17`, producing per-knowledge-point `mastery_levels`, with a sibling `mastery_learning_evidence` table at `storage.py:584` holding the per-attempt evidence. `RepetitionState` at `learning/models.py:202` still describes the review schedule. Port those into Rust types over `rusqlite`. Event sourcing gives undo and audit for free.

**Job.** One agent invocation with a prompt, an optional JSON schema, a workdir, a capability set, a timeout and a resumable session id. The drivers worker proposed the contract below; under the Rust decision it is real Rust rather than a Python provider.

```rust
#[async_trait::async_trait]
pub trait AgentDriver: Send + Sync {
    fn id(&self) -> &'static str;
    fn capabilities(&self) -> Capabilities;
    async fn start(&self, job: JobSpec) -> anyhow::Result<JobHandle>;
    async fn resume(&self, session: &str, job: JobSpec) -> anyhow::Result<JobHandle>;
    fn events(&self, h: &JobHandle) -> EventStream;
    async fn cancel(&self, h: &JobHandle) -> anyhow::Result<()>;
}
```

The truth rule that ties these together. Content lives in files the agent writes. Progress and annotations live in SQLite. Neither is derived from the other, so regenerating a chapter never silently destroys your marks.

## Ingestion and the Rust crate choices

Decisions 5 and 9 made this a feasibility question, so it got its own slice. All versions below were verified against the crates.io API on 2026-11-08.

**PDF highlights are feasible in pure Rust.** This was the largest unknown under the port-to-Rust decision, and it resolves positively. `pdf-extract` 0.12.1 (MIT, pure Rust, built on lopdf) looks like a flat-string extractor only because its convenience `extract_text` helper returns strings. Its public `OutputDev` trait is the real interface, and I verified these signatures independently on docs.rs:

```rust
fn begin_page(&mut self, page_num: u32, media_box: &MediaBox,
              art_box: Option<(f64, f64, f64, f64)>) -> Result<(), OutputError>;
fn output_character(&mut self, trm: &Transform, width: f64, spacing: f64,
                    font_size: f64, char: &str) -> Result<(), OutputError>;
```

`trm` is the text rendering matrix, so it carries per-glyph position and scale. `MediaBox` carries the page dimensions. `begin_word`, `end_word` and `end_line` give grouping for free. A custom `OutputDev` therefore yields page, character, position, width and font size, which is enough to store an anchor as page number plus quote text plus a normalized rect. No pdfium, no C or C++ toolchain, no native binary download.

One caveat follows from the signature. No font ascent or descent is passed, so glyph box height must be approximated from `font_size`, roughly 1.0 to 1.2 times the em. That is fine for highlight rectangles and not fine for pixel-perfect glyph outlines. Extraction quality on exotic encodings is unbenchmarked; `pdfium-render` 0.9.5 is the fallback behind the same trait if real PDFs disappoint, at the cost of a C++ binary download. `mupdf` 0.8.0 is rejected twice over, AGPL-3.0 and a native C build.

**URL ingestion needs no crate.** Delegate it to the coding agent. The agent already fetches pages and writes markdown, so a Rust extractor would duplicate work the agent does better. `readability` 0.3.0 is stale at 2023; `dom_smoothie` 0.19.0 (MIT, pure Rust, active) is the fallback if delegation proves unreliable. Ship nothing in v1.

**Markdown needs no Rust parser by default.** The agent writes markdown and the TypeScript UI renders it, so parsing it twice is waste. Add `pulldown-cmark` 0.13.6 (MIT) only if Rust must read heading structure to build the sidebar tree, and even then the tree can come from `course.json` instead.

**Storage and process.** `rusqlite` 0.41.1 (MIT) with the `bundled` feature compiles SQLite in, so there is no system library dependency; `bundled-sqlcipher` exists if you later want encryption. `tokio` 1.54.1 (MIT) spawns the agent CLIs with piped stdout, reads NDJSON through a `BufReader` lines stream, and cancels with `kill_on_drop` plus an explicit kill.

| Need | Crate | Version | License | Native dep |
|---|---|---|---|---|
| PDF text with positions | pdf-extract | 0.12.1 | MIT | None |
| PDF fallback only | pdfium-render | 0.9.5 | MIT OR Apache-2.0 | Pdfium C++ binary |
| URL to article | none, delegate to agent | n/a | n/a | None |
| Markdown in Rust | pulldown-cmark, only if needed | 0.13.6 | MIT | None |
| SQLite | rusqlite, `bundled` | 0.41.1 | MIT | None, compiled in |
| Agent subprocess | tokio | 1.54.1 | MIT | None |

Nothing in the v1 set drags in a heavy native toolchain. That was the point of the slice, and it holds.

## The JS-on-Rust mechanism

This answers your explicit question. Rust never interprets JavaScript.

Tauri v2 (stable **2.12.5**, verified against crates.io on 2026-11-08) embeds the OS webview through **wry 0.57.1**. On macOS that is Apple's `WKWebView`; wry calls the WebKit Objective-C API (`WKWebView`, `WKWebViewConfiguration`, `WKURLSchemeHandler`) so you never write Swift yourself. Rust serves the bundled frontend over an in-process custom protocol, `tauri://localhost` on macOS and Linux, `http://tauri.localhost` on Windows. The agent's three.js, canvas, SVG and D3 then execute inside WebKit's JavaScriptCore exactly as they would in Safari. `canvas.getContext('webgl2')` is supplied by WebKit, which has run WebGL2 on Metal since Safari 15 (webkit.org, 2021-10-26). This machine runs macOS 27.2, far newer.

A custom protocol rather than `file://` matters because `file://` gives an opaque origin that breaks ES-module `import`, `fetch` and CORS. A custom scheme behaves like a real origin, so modules work offline.

**That holds for the top-level document, not for a sandboxed iframe, and ticket 01 measured the difference.** Running the real app over the production `visual://localhost` scheme, an `<iframe sandbox="allow-scripts">` without `allow-same-origin` reports `webgl2: true` with renderer `Apple GPU`, but importing the vendored `three.module.min.js` sibling fails with `TypeError: Importing a module script failed.` Over the dev server at `http://localhost:1420` the same fixture imports and renders, 24 frames at three revision 169. The cause is that omitting `allow-same-origin` makes the iframe an opaque origin, so a sibling module import is cross-origin even though the custom scheme itself is a real origin. WebGL2 is not the problem and the zero-capability-webview fallback is not triggered by it. Ticket 08 owns the fix; the likely direction is inlining the vendored module source into the artifact's own inline module script, which the artifact contract already requires for CSS, JS and SVG, rather than importing it as a sibling. A localhost HTTP server would also work but opens a TCP port any local process can reach; the custom protocol is in-process and not network-reachable.

IPC is `#[tauri::command]` plus `invoke()` from TypeScript for requests, `app.emit()` plus `listen()` for pushes, and `tauri::ipc::Channel<T>` for streaming (v2.tauri.app/develop/calling-rust/).

Slint, Iced, egui and Makepad cannot render arbitrary third-party JavaScript at all, because they have no JS engine. That rules out the pure-Rust-UI family for this app regardless of preference.

### Sandboxing agent-generated artifacts

Agent output is untrusted. Tauri v2 denies every capability by default and scopes grants by window/webview label, so an artifact webview whose label appears in no capability file cannot call `fs`, `http` or `shell`. The posture is a trusted reader window with capabilities, plus one zero-capability webview per artifact, plus `<iframe sandbox="allow-scripts">` without `allow-same-origin`, plus a tight CSP, plus a custom-protocol handler that maps a fixed allowlist of artifact IDs to bytes and never exposes a general file path.

One caveat you inherit on Linux. The capabilities docs state that "On Linux and Android, Tauri is unable to distinguish between requests from an embedded `<iframe>` and the window itself", so there the iframe is not a reliable IPC boundary and isolation must come from separate zero-capability webviews. macOS and Windows hold the iframe origin isolation.

## The visual artifact contract

Two workers converged on this independently, which is high signal. The visual-skills worker derived it from visual-explainer's rendered output; DeepTutor already ships nearly the same protocol.

One visual is a directory under its chapter holding `index.html` with inline CSS, JS and SVG, plus `manifest.json`. Zero network. No CDN, no Google Fonts, no `fetch`. For 3D, a vendored `three.module.min.js` pinned to r169 is the only allowed sibling script. The host loads it in a sandboxed iframe and sends `init` with chapter data by `postMessage`; the visual replies `ready`, then reports `quiz.answer`, `progress`, `select` and `error`. A static validator rejects any external URL before display, and a 3-second `ready` timeout falls back to the markdown rendering of the same concept.

| Source | Verdict | Reason |
|---|---|---|
| nicobailon/visual-explainer | Adopt as primary | Emits one self-contained HTML and has a render step that validates in a browser and lists errors to fix. Must vendor or strip the Google Fonts injected at `kit/render.mjs:161-163` and ban CDN libraries. |
| Moh4696/open-3d-skills | Adapt for 3D | Best skill text, pure-code three.js with no model files. Starter imports three from jsdelivr at `index.html:12-13`; vendoring r169 makes it offline with no build step. |

## Agent drivers

Six agent CLIs are installed here. I verified the binaries myself. Three are confirmed drivable headlessly against an existing subscription with no new API key.

| Agent | Version | Keyless headless | Caveat |
|---|---|---|---|
| claude | 2.1.319 | Yes, Pro/Max OAuth is the default | A set `ANTHROPIC_API_KEY` overrides it into pay-as-you-go. The Rust driver must scrub that env var before spawn. |
| qoder / qodercli | 1.1.85 | Yes, browser OAuth against plan quota | No `--json-schema` in help, so structured output is prompt-enforced and validated after parse. |

| grok | 1.0.70 | Login path exists | Headless quota behavior unverified. |
| cursor-agent | 2026.10.16 | Login path exists | Staff acknowledged `CURSOR_API_KEY` misbehaves headless. |
| opencode | 1.19.3 | Provider-key centric | Subscription passthrough unverified. |

`codex` and `gemini` are absent on this machine. Do not design against them.

The reference invocation, with flags captured from local `--help`:

```
claude -p "<prompt>" --output-format stream-json --include-partial-messages \
  --json-schema '<schema>' --permission-mode plan --append-system-prompt "..."
```

Google explicitly blesses the equivalent for agy. An official responder in Google's forum states that calling the official `agy` binary locally via `agy -p` is an officially supported feature built for programmatic scripting. Anthropic's and xAI's terms on third-party wrapping were not verified; the safe framing is that you run your own licensed CLI on your own machine.

Ship the three verified drivers first. Default to claude for its structured output, fall back to qoder or agy. Probe `--help` and `--version` at startup and degrade capabilities gracefully, because all six CLIs auto-update. Never hardcode a flag without a version probe.

**The env scrub is our addition, not a port.** I grepped `claude_code_provider.py` for `env=`, `environment` and `ANTHROPIC_API_KEY` and the only hit is the `sdk.ClaudeAgentOptions(` construction at `:529`. Upstream passes no child environment and scrubs nothing, so the child inherits the parent's variables and upstream's keyless behavior simply assumes no key is set. The Rust driver must build the child environment explicitly and remove the metering variables. Porting the file as written would silently inherit the bug.

## What we drop

From Notion, per the Ghidra evidence: the web-wrapper architecture and its remote origin, the ~480 KB preload chunk duplicated into every window, the auxiliary window sprawl (`activity_monitor`, `meeting_notification_pill`, `speaker_and_microphone_status`, `sqlite_browser`), the `clientMcpHost` iMessage and filesystem tool surface, the Electron framework zoo (Squirrel, Mantle, ReactiveObjC, four helper apps), and Chromium's storage zoo plus the opaque 92 MB `notion.db`. Calendar, Notion AI, hand-built databases and manual tags go, as you asked.

From DeepTutor: `services/imagegen`, `services/videogen`, `agents/math_animator` (Manim drags in Python + LaTeX + ffmpeg), `agents/video_lesson` (Remotion plus TTS), `book/` and `co_writer/` (authoring surfaces, and you chose a reader), the seven-engine parsing stack in favour of three formats, the whole RAG and embedding layer in favour of agent-driven retrieval, and `services/memory/` consolidation machinery, which is more than a solo v1 needs.

From the feature list: EPUB and image OCR are out of v1. A mock-interview conversation mode is out. A flashcard mode is out. A search index is out. Each was cut by an explicit decision, not deferred silently.

**snap-stanford/memorilla is rejected.** You flagged it as interesting, and it is interesting, but it does not earn a place here. I verified this in the repo rather than trusting the worker. It is a Stanford SNAP research system implementing arXiv:2610.21375 that compresses a whole document collection into 16 query-dependent latent memory tokens for a frozen Qwen3-8B (`README.md:13-18`). "Memory" there means context compression, not remembering a learner's progress. It has no SQLite, no mastery model, no spaced repetition and no concept of a learner. Its installation section requires Linux with CUDA GPUs and Python 3.11, run on NVIDIA H100 80GB, and the first run downloads about 25 GB of models (`README.md:43,78-79`). That conflicts with four locked decisions at once: no embeddings, Rust core with no Python sidecar, macOS first, and no dedicated model. Only its PV4 question rule is worth taking, and that is a prompt constraint recorded above.

## Verification plan

You will not read code, so these are checks you can actually perform.

**Spike 1.** Does WebGL2 run inside a `sandbox="allow-scripts"` iframe in a Tauri WKWebView on this machine? This is the one untested assumption that decides whether the 3D tier exists. If it fails, the fallback is a separate zero-capability webview per artifact instead of an iframe.

**Spike 2.** Does a keyless `claude -p` job consume subscription quota rather than API credit, with `ANTHROPIC_API_KEY` scrubbed? The support article documents the precedence but does not name print mode explicitly. One real job settles it.

**Spike 3.** Extract a real lecture PDF with a custom `pdf-extract` `OutputDev` and check that the normalized rects land on the right words. The API feasibility is now confirmed from the documented signatures, so this spike tests extraction quality on your actual documents, not whether the approach is possible.

**Feel test.** After the first chapter renders, read it for 20 minutes and highlight five passages. Then regenerate that chapter and check whether the five marks re-anchored and whether the failures were surfaced honestly. This is the acceptance gate for the whole product, because it tests the thing you said you hated about scattered tools.

**Clutter test.** Count the visible controls in the reader chrome. Notion's auxiliary-window sprawl is the negative reference. If the count grows past a handful, the UI is drifting back toward the thing you are escaping.
